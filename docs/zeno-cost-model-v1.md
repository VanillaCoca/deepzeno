# ZENO 成本模型 v1

> 状态：已定稿，正在实施
> 日期：2026-07-26
> 一句话：**先做「不亏钱」，不做「收钱」。收钱层留接口，等公司注册好再插。**

---

## 0. 这份文档在回答什么

原始需求是一句话：「我的 credit 能 cover 的部分，活动期间免费给大家用；需要我本人承担成本的部分，交给用户自己来。」

要把这句话变成代码，必须先回答三个它没说的问题：

1. 「我的 credit 能 cover 的部分」——**以什么为单位度量？** 现在系统里唯一的限流是 `maxMessagesPerHour: 10`，它把一次 DeepSeek 调用和一次 Opus 调用算成同一件事，而两者成本差两个数量级。用错的单位限流，等于没限流。
2. 「交给用户自己来」——**用什么机制交？** 让用户付钱给你，还是让用户直接付钱给模型厂商？这两条路的法务成本差着一个公司注册。
3. 你说的是「**盈利**」，但你给的原则是「**不亏钱**」。这两件事不是同一件事，下面第 3 节单独说。

---

## 1. 最关键的发现：成本不是一种，是两种

把系统里每一处会烧钱的地方列出来，它们自动分成两堆：

**一次性成本（one-shot）**：一条 chat 消息、一次 sweep 抽取、一次 kickoff、一次 L2 调研。
共同特征是 **必须有人按一下**。它有天然上限——人的手速和注意力。免费额度可以吸收它，因为它的总量被人的行为封顶了。

**常驻成本（standing）**：L3 Watchtower 巡检。
共同特征是 **按一下之后永远收费**。更糟的是 `suggestWatchForNode` 会在每次调研结束后自动为每个有证据支撑的节点创建 watch——用户一次都没按过，成本就已经产生了，而且永不退休。

这个切分直接给出第一个结论：

> **免费额度可以吸收一次性成本，结构上无法吸收常驻成本。** 因为常驻成本对时间的积分是发散的。

### 1.1 这恰好就是昨天那个队列饥饿 bug 的根因

昨天查出来的问题是：一条 cron，8 次巡检/天，而 watch 数量只增不减；一旦超过 8 个，界面上写着「每天巡检」的 watch 实际上可能一个月才轮到一次，**而系统什么都不说**。

现在可以给它一个更准确的名字：**免费层在偷偷地给一个无上限的常驻成本做限流，用「排队」代替了「说不」。** 系统本该说「你的免费额度只够养 8 个 watch」，它却让 40 个 watch 都显示「每天」，然后每个 40 天才轮到一次。

**限流是诚实的；假装不限流才是欺骗。**

所以：盈利模型和队列饥饿是同一个问题的两面。修一个就是修另一个。这也是为什么这次改动的落点在 Watchtower 而不在 chat。

## 2. 两个硬约束（都已核实，不是推测）

### 2.1 Vercel Hobby 明文禁止任何商业用途，连接受捐赠都算

Vercel 的 Fair Use Guidelines 原文：Hobby team 限于非商业的个人用途，商业用途的定义是「任何以参与该项目生产的**任何人**获得经济利益为目的的 Deployment」，举例第一条就是「向站点访客请求或处理付款的任何方式」，并且明确注明「请求捐赠也属于商业用途」。

这意味着：**在 app.deepzeno.ai 上放任何收款入口的那一刻，就违反了 Vercel 的服务条款**，风险是整个部署被下线。

反过来说，**BYOK 完全不触发这一条**——它不处理任何支付，钱是用户直接付给 OpenAI/Anthropic/DeepSeek 的，平台连中间人都不是。

### 2.2 没有美国公司，能用的收款通道只有一条

| 通道 | 是否 MoR | 中国大陆个人能否做卖家 | 结论 |
|---|---|---|---|
| Stripe 直连 | 否 | 需要注册实体，大陆不支持 | 现在排除 |
| Polar | 是 | 底层用 Stripe Connect Express 打款，不支持大陆 | 现在排除 |
| Lemon Squeezy | 是 | 同上（已并入 Stripe） | 现在排除 |
| Paddle | 是 | 要求企业实体验证 | 现在排除 |
| **Creem** | **是** | **支持，86 国含中国大陆，本地银行转账** | **唯一可用** |

Creem 费率 3.9% + $0.40，前 €1,000 收入 0%；打款手续费 7 USD 或 1% 取高。

MoR（Merchant of Record）的意义：**它在法律上是卖家**，替你处理全球 VAT/销售税申报、开票、退款、拒付。个人开发者不可能自己做这件事——不是麻烦，是做不了。

## 3. 必须直说的一个差距：你说的是「盈利」，你给的原则是「不亏钱」

「把成本转嫁到用户那里去」是成本转嫁，不是收入。BYOK 做到 100% 的成本转嫁，产生 0 元收入。

要盈利，必须有人付钱给你，而付钱给你需要（a）Vercel Pro 解禁商用，（b）一条 MoR 通道，（c）一个值得付费的差异化——而目前唯一真正稀缺的资源是**巡检产能**，不是模型调用（模型调用用户自己接 key 就有了）。

所以我的判断是：**现在不做收入层，但把它的接缝留好。** 理由不是「以后再说」，而是：

- 收入层今天上线会违反 Vercel 条款，风险 > 收益；
- 你还没有可收费的稀缺资源（产能问题下面第 5 节会用零成本的办法解决掉一大半）；
- 一旦你想收，代码侧只需要填一个 `plan` 字段的来源和一个 webhook，不需要重构。

## 4. 三层结构

### Layer 0 —— 平台垫付（活动期免费）

每个用户每月一份 **以美元计** 的额度。为什么是美元不是「多少条消息」：见第 0 节第 1 点。

额度用完时，**不降级、不变慢、不排队**，而是明确地说：

> 本月平台额度已用完。接上你自己的 API key 就能继续，用量不再受限。

这句话是整个模型的转轴。它同时做到了三件事：说了真话、给了出路、把成本交了出去。

**两个例外，以及为什么它们不是例外。** 实现的时候有两条路径最终是「降级」而不是「拒绝」：语义搜索退回关键词匹配，建项目时的抽取退回启发式抽取。判断标准不是省钱，是**这条路径有没有一个诚实的、更便宜的版本**：

- 调研、巡检、sweep、kickoff、批量导入——**没有**。半次调研不是调研，返回一个残缺结果比返回「额度用完了」更糟，因为用户会把它当成完整结果用。这些一律 402。
- 搜索和建项目抽取——**有**。关键词匹配和 `heuristicExtract` 本来就存在，是「没配 provider」时的兜底路径，不是为了省钱临时凑的。这时候拒绝，等于为了跟别的路由保持一致而主动选择「没有」而不是「差一点」。而建项目是用户在这个产品里做的第一件事，把门堵上换几分钱的抽取，是错的那一边。

降级的前提是**不许悄悄降**。两条路径都在响应里带 `allowance_exhausted`，UI 上都明说排序/抽取被关掉了、以及开关在哪儿。悄悄降级正是 Iron Law 2 要防的那种「漏而不声张」——用户会以为产品变笨了，而不是知道自己撞到了额度。

### Layer 1 —— BYOK（用户自带 key）

用户在设置里粘贴自己的 provider key，AES-256-GCM 加密入库，明文永不回传。带 key 的用户：

- 所有 AI 调用走他自己的 key，**不消耗平台额度**；
- 因此没有月度美元上限；
- L3 watch 配额从 5 提到 20，但**不是无限**（`byokMaxActiveWatches: 20`）。

这是「需要我本人承担成本的部分交给用户自己来」的字面实现。

最后一条是这份文档写完之后改的，值得说明为什么：watch 花的不只是钱。每条 watch 每天要占掉那唯一一次 cron 扫描里的一个名额，而扫描产能（现在 24/天）是**全体用户共享**的，跟谁出钱无关。「BYOK 就无限」意味着一个自带 key 的用户可以合法地把当天的巡检队列全部占满，让其他所有人的 watch 静默地过期不跑——正好是 Iron Law 2 里最坏的那种「漏而不声张」。所以配额分两层：美元额度按出资人分，**产能名额按人头分**。20 是半天产能，一个租户可以拿走一半，拿不走全部。

#### key 失效时会发生什么（这一条是 BYOK 的必答题）

用户的 key 会死：被吊销、被换掉、账户欠费。这不是异常分支，是必然会发生的事，所以「key 死了之后系统怎么走」和「key 活着的时候怎么走」同等重要。

在 BYOK 之前，一次 provider 调用失败只有一种含义。所有调用都跑在平台自己的 key 上，401 和 503 的出资人相同、正确应对也相同：熔断，换一家重试。BYOK 把这一个命题劈成了两个，而且答案相反：

- **503 是 provider 的问题**——熔断器和降级路径本来就是为它写的，照旧。
- **401 是这一个租户的凭据问题**。此时熔断会让一个用户的坏 key 把整个部署的这家 provider 电路打开，误伤所有其他人；降级重试则会把这次调用挪到用户没有 key 的另一家 provider 上，也就是**挪回平台额度**——一个明确选择了自付的用户，反而开始花我的钱，而且他永远不会知道自己的 key 已经死了。两件事都是静默的，这正是它们比原始错误更糟的地方。

所以 `classifyProviderFailure`（`lib/ai/provider-failure-core.ts`）把失败分成 `credential | capacity | endpoint` 三类，只在前者上改变行为：

- 用户 key + credential 失败 → **不碰共享熔断器，不降级，直接抛**；同时 `providers.ts` 里的中间件把这把 key 标成 `invalid` 并写下原因，设置面板立刻显示「Not working」。**下一次**调用因此落回受限的免费额度——降级了，但是出声的。
- `429` 归入 `capacity` 而非 credential：限流恰恰是这把 key **真实有效**的正面证据，在这里禁用它等于因为用户成功使用产品而惩罚他。
- 只有 `401 / 402 / 403` 算 credential，刻意收窄。把 404 或 5xx 读成「你的 key 坏了」会禁用一把好 key——Iron Law 2 防的是「编造」甚于「遗漏」，而一把被误禁的 key 是一个需要用户手工撤销的、被凭空发明出来的故障。402 放在这里而不是 capacity，是因为用户的下一步动作和吊销完全一样：去 provider 那边处理，产品这边重试多少次都不会让余额变多。

另外一个刻意的设计：写进 `provider_keys.last_error` 的那句话只由**状态码和 provider 名**合成，绝不取自 provider 的响应体。那个字段会原样渲染回用户界面，而 provider 的错误体经常回显请求上下文、偶尔回显 key 前缀——一旦漏进来，就会明文躺在数据库里再也不会消失。单测里有一条专门断言这件事。

### Layer 2 —— 常驻成本单独设限

L3 watch 是系统里唯一的常驻成本，所以它有独立于美元额度的配额：免费用户 N 个 active watch。超出时：

- 用户**手动**添加的 watch → 直接拒绝，并在同一处说明原因和解法；
- `suggestWatchForNode` **自动**创建的 → 不创建，但**必须留下可见记录**。Iron Law 2 允许漏，不允许沉默——所以要写进事件流，并在节点上能看到「因配额未开启监测」。

N 从产能反推，不拍脑袋：**配额不能承诺超过产能。**

### Layer 3（未来）—— 收款

留接口不留实现。触发条件：你决定要收钱的那天。

### 记账的粒度：`usage_ledger.kind`

每一笔计量都要标明是哪类调用：`chat | research | patrol | sweep | kickoff | search | import`。

比 run 的类型更宽，是因为有三类花费根本没有 run 行：`chat` 没有、`kickoff` 发生在项目的第一个 run 之前、`search` 永远不会有——语义排序是一次前台查询，不是一次 run。

`search` 和 `import` 是这一轮补上的。它们本来可以塞进 `chat` 里省一列，但那样会毁掉运营唯一真正需要的那个数：**一次对话到底花我多少钱**。一次点搜索框和一次对话的成本结构完全不同，混在一起之后这个数就再也读不出来了。记账的分类不按代码结构分，按「以后要回答什么问题」分。

## 5. 一个不用花钱的产能提升（必须先做，因为它决定 N）

现在 cron 里是：

```ts
for (const watch of due) {
  await runPatrolForWatch({ watchId: watch.id });
}
```

串行。但巡检是 **I/O 密集**——绝大部分时间在等模型和搜索接口返回，不是在烧 CPU。在同一个 300s 预算里做**有界并发**，产能从 8/天 提到 24/天，**花零元**。

这一点推翻了昨天那个「降需求 vs 提产能」的二选一：**提产能根本不需要花你的钱。** 所以两件事都做。

已实现的数是 `sweepConcurrency: 4` × `maxWatchesPerSweep: 24` × `sweepsPerDay: 1`。写 24 不写 40，是因为 40 那个估计假设四条并发都能跑满整个 300 秒；真实的巡检长度方差很大（要等外部搜索），留出的余量是给最慢的那条尾巴的。并发上限也不是越大越好：每条并发都对同一批搜索和模型端点持有连接，多到一定程度，一个部署就变成所有租户共同的限流问题。

### 5.1 但提产能治不了根因：需求是单调增的

上面那段只动了供给一侧，而供给是**常数**——一天固定几次巡检。需求一侧是 `watch-suggest.ts`：每出现一个有证据支撑的节点就加一个 watch，而**没有任何路径会撤掉一个**。常数供给对单调增需求，饱和不是风险，是时间问题；并发从 8 提到 24 只是把交叉点往后推了三倍，没有改变它一定会到来。

真正该攻击的是 **FIFO**。一条排满的队列把槽位均匀地花掉，于是「三个月没动过的主张」和「每周都在变的主张」抢同一个槽——每天抢，永远抢。稀缺的从来不是钱，是注意力，而注意力应该流向产出高的地方。系统手里唯一关于产出的证据，就是**连续多少次巡检什么都没发现**，所以间隔从它推导：

```
interval = min(cadence × 2^⌊quiet/3⌋, 30 天)
```

四个刻意的取舍：

- **不改 `cadence` 本身。** cadence 是用户选的那个承诺；改掉它，恢复时就得记住原值。用「承诺 + 计数器」推导，任何一次有发现都能把承诺**精确**还原，没有要记的状态，也就没有会漂移的状态。
- **失败的巡检不算 quiet。** key 挂了、搜索接口 500、页面超时——这些是关于产品的证据，不是关于世界的证据。把它们算进去，一个坏掉的 provider 就能让全站的 watch 悄悄退化到每月一次，而症状要几周后才以「Zeno 好像不再发现东西了」的形式出现，中间没有任何记录把两者连起来。
- **封顶 30 天，但永不退休。** 一年 365 次巡检压到十几次，常驻成本已经被压住了；退休也能压住，但那是**静默地放弃覆盖**，正是 Iron Law 2 明令禁止的。上限存在的意义是：无论沉默多久，「还有人在看」这句话仍然为真。
- **退避和拥堵在 UI 里是两句话。** 一句是可逆的决定（值得解释），一句是产能不足（值得警告）。合成一句的话，用户无法分辨自己看到的是哪一种，也就无法判断自己做什么有用。`isCadenceHonored` 因此改成拿队列去比**退避后**的间隔，而不是比原始 cadence——否则它会为一个系统主动做出的决定发出「队列跟不上」的警报。

**`maxActiveWatches` 这次不动。** 退避把有效承载量抬高了一个数量级，看起来正是放宽 N 的时机——但 §4 的规矩是「N 从产能反推，不拍脑袋」，而反推的诚实输入是**线上观测到的 quiet 比例**，不是我在这里估的一个模型。那件事是 #57，它还卡在没有观测数据上。在拿到数据之前把 N 调大，就是用一个新的拍脑袋去替换旧的拍脑袋。

## 6. 实施顺序（依赖倒序，不是重要性倒序）

1. **给 L3 装计量。** `lib/research/patrol.ts` 现在写着 `costEstimate: () => null`——注释还诚实地说「巡检不是免费的，是没被测量」。**没有计量就没有配额**，这是所有其他事情的前置。
2. **额度与出资判定**（纯逻辑 + 单测）：`decideFunding({plan, spentUsd, hasOwnKey})` → `platform | byok | denied`。
3. **两张表**：`usage_ledger`（追加式记账）、`provider_keys`（密文）。
4. **BYOK 路由**。最大的一块重构：`lib/ai/providers.ts` 现在把所有 provider 在**模块加载时**从 `process.env` 构造，per-user key 必须把 key 上下文穿进 `getLanguageModel`。
5. **准入控制 + 有界并发**。
6. **验证与提交。**
